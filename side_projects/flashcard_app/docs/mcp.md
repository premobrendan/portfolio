# The Flashcards MCP server

Lets a model create and edit packs in your local library — the same library the app reads,
through the same code the app writes with.

## What it is

A small Node process you register with your own Claude client. It is **not** bundled into
the app and the app does not launch it. It talks
[MCP](https://modelcontextprotocol.io) over stdio, runs only while your client is running,
and costs nothing to operate — it reads and writes files in your own library folder.

It imports `electron/storage.ts` directly, which has no Electron dependency. So a pack a
model writes goes through the same `savePack` as a pack you type by hand, and is held to the
same validation: **every card needs a Front Text and a Back Primary Text.** There is no path
by which a model can write a pack the app would reject.

## Setup

Build the server once:

```bash
npm install
npm run build:mcp
```

That produces `dist-mcp/server.mjs`, a single self-contained file.

Then register it with your client. For Claude Code:

```bash
claude mcp add flashcards -- node /absolute/path/to/flashcard_app/dist-mcp/server.mjs
```

Or add it to the MCP config your client reads:

```json
{
  "mcpServers": {
    "flashcards": {
      "command": "node",
      "args": ["/absolute/path/to/flashcard_app/dist-mcp/server.mjs"]
    }
  }
}
```

Re-run `npm run build:mcp` after changing anything under `mcp/`, `electron/`, or `shared/`.

## How it finds your library

In order:

1. `FLASHCARDS_USER_DATA` in the environment.
2. `--root /path/to/library` on the command line.
3. `~/.flashcards/library.json`, which the app writes on every launch.

If none of those resolve, the server exits with a message rather than starting. **It never
guesses.** The library lives at Electron's `userData` path, which is derived from the app
name — and that name differs between a dev run and a packaged build. A wrong guess would
silently create a second, empty library, which looks exactly like the app losing your packs.

So: **launch the app once before first use.** After that the pointer is on disk and the
server finds it.

## Tools

| Tool | Does | Notes |
|---|---|---|
| `list_packs` | Summaries: id, name, card count, whether you have unsaved work open | Cheap. Start here. |
| `read_pack` | Every card in one pack | Large. Only when the card text is actually needed. |
| `create_pack` | New empty pack, returns its id | Invisible to Pack Selection until it has cards |
| `add_cards` | Append cards and save | The main write. Batch them. Returns the new card ids. |
| `update_card` | Change one card in place | Fix a typo without resending the pack |
| `replace_all_cards` | Replace the entire card list, optionally rename | Destructive: anything omitted is deleted |
| `delete_pack` | Destroy a pack and all its backups | Requires `confirm: "DELETE"` |

Card ids are generated by the server. A model supplies `front`, `primary`, and optionally
`secondary` and `moreInfo` — both unvalidated.

`secondary` is a *second* fact about the same subject: primary "He was the 16th president",
secondary "He issued the Emancipation Proclamation". When a card has one, the two compete
for the back of the card, so a single card can quiz either fact. Pass `secondary: ""` to
`update_card` to remove it, the same as `moreInfo`.

**The three write tools are deliberately distinct**, because the cost of picking the wrong one
is silent data loss:

- `add_cards` **appends**. Existing cards are untouched.
- `update_card` **edits one card**. Omitted fields are left alone; `moreInfo: ""` removes it.
  Card ids come back from `add_cards`, so editing something you just wrote costs no extra read.
- `replace_all_cards` **deletes everything you did not include.** It is named for what it
  destroys rather than for what it saves, because "save" is the verb a model reaches for when
  it means "append" — and that mistake would empty the pack.

## Two guards worth knowing about

**Drafts are protected.** Leaving the Make a Pack editor without saving keeps your work as a
draft, and a save discards that draft. So a write from the MCP server to a pack you have open
and unsaved would destroy your work. Those writes are **refused**, with a message telling the
model to ask you to save or leave that pack first. `force: true` overrides it — that is the
model choosing to overwrite your unsaved work, so it should ask you before using it.
`list_packs` reports `hasUnsavedDraft` so it can see the situation before trying.

**Deletion needs the word.** `delete_pack` requires `confirm: "DELETE"`, mirroring the
type-DELETE gate in the app. An irreversible action should not be one malformed tool call
away.

## Keeping it cheap

Tool results land in the conversation and are re-sent on every later turn, so a chatty
integration burns through usage faster than it needs to:

- Send every card in **one** `add_cards` call. A call per card re-sends the whole
  conversation each time.
- Prefer `list_packs` over `read_pack` when you only need to know what exists.

## Testing

```bash
npx vitest run mcp/          # handlers, guards, and the on-disk round trip
```

The handlers in `mcp/tools.ts` are plain async functions with no MCP types, so they are
tested directly against a temp library. `mcp/server.ts` is only wiring.
